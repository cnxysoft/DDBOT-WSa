# 图片与传输大小约束

核对日期：2026-11-15。

- NapCatQQ 备份 fork `ZoeRift805/NapCatQQ`，提交 `72912f293924f43463b5976b01fc094a8ae11481`。
- LLOneBot 上游 `LuckyLilliaDev/LuckyLilliaBot`，提交 `de602971f850c3965a9b348e7d1f3e723eb1eba7`。

两个版本的普通图片发送路径都只明确拒绝空文件，将原文件大小、宽高交给 QQ 上传接口。
源码中没有普通图片 30MB/30MiB、最大边长或总像素的固定校验。最终是否接受仍取决于 QQ；
不能据此认为图片没有上限。LLOneBot 的 `TriSha1` 中 30MiB 是文件哈希采样阈值，
WebQQ 的 10MiB 校验仅适用于网页上传，都不是 OneBot/Satori 的单图上限。

NapCatQQ 的独立正向、反向 WebSocket 实现配置 `maxPayload: 50 * 1024 * 1024`，
即整条入站消息最多 52,428,800 字节，包含 JSON 和 Base64。相关源码为
`packages/napcat-onebot/network/websocket-server.ts` 和 `websocket-client.ts`。
30MiB 原图编码后约 40MiB；两张各 20MiB 的图片一起编码就会超过该上限。

DDBOT 的 OneBot 适配器据此对普通消息追加字节分片：按实际 JSON 元素长度计算，
为请求包装预留 4KiB，保留原消息边界和元素顺序。发送前还会检查完整请求，
不可拆分的超大元素或合并转发请求会在写入前返回明确拒绝，避免超限断连后投递结果不明。
现有 150MiB WebSocket 接收上限用途不同，继续保留。

最新 LLOneBot 的 OneBot WebSocket 使用 `maxPayload: 0`；OneBot/Satori HTTP 已改用 Hono，
上述提交没有显式请求体大小中间件。旧版本的 Satori Express `50mb` 限制不能作为最新
上游约束。未声明载荷上限的适配器保持原有分片行为；部署旧服务时仍应核对其版本和限制。

图片合并产物的 30MB 输出策略与上述传输预算需要分别处理，不能混用常量。
分辨率上限需要通过实际发送及客户端查看验证。

## 当前运行服务的实测

2026-11-15，使用 LLOneBot 8.3.2 的群图片上传路径测试。通过本地文件 URI 提交，
排除 Base64 编码与请求体大小的影响。OneBot v11 与 Satori 均连接同一个运行后端，
不代表两套独立的 QQ 实现。

| 原始文件大小 | 测试图片 | 结果 |
| --- | --- | --- |
| 29,507,395 字节 | PNG，3200×3072 | 成功，CDN 原图大小与 SHA-256 一致 |
| 32,014,358 字节 | PNG，3200×3333 | 成功，CDN 原图一致；本机 QQ 图片查看器可打开 |
| 32,961,069 字节 | JPEG，3200×5208，Satori | 成功，CDN 原图大小与 SHA-256 一致 |
| 33,554,432 字节（32MiB） | PNG，3200×3489，OneBot | 成功，CDN 原图大小与 SHA-256 一致 |
| 33,554,433 字节（32MiB + 1） | PNG，3200×3489，OneBot | Highway 上传失败，code 323；OneBot retcode 1200 |
| 33,969,437 字节 | JPEG，3200×5364，Satori | HTTP 500，Highway 上传失败，code 323 |

精确边界的两张 PNG 使用相同像素与宽高，只调整合法的 PNG `tEXt` 块长度，
重新计算 CRC，并在发送前完整解码验证。因此当前路径的失败边界可以归因于文件字节数，
不是像素或分辨率变化。32MiB 样本的原文件与 CDN 原图 SHA-256 均为
`363df59a69a857d9162bb748f5bf8456acd27afa19d3d219c4f5696c5a8f3790`。

这证明当前内部上传路径仍有大小限制，且允许超过十进制 30MB 的图片；不能将其推广为
QQ 的统一协议承诺。未验证 NapCat 运行实例、私聊、其他账号或独立接收设备，
也未确定最大边长和总像素边界。合并产物仍建议采用严格小于 30,000,000 字节的兼容策略，
不因这一次实测提高默认预算。

另有 33,512,781 字节的 PNG 请求在等待 100 秒后超时，但随后出现在群历史中，
CDN 原图亦验证一致。发送超时必须视为结果不明，不能自动重试，以免重复投递。
原始响应、测试程序与样本保存在被 Git 忽略的 `debug/image-boundary/`，
不把临时 CDN 链接和群聊标识纳入文档。

## 共享图片合并的端到端验证

同日通过项目实际 `notify.group.xhs.news.tmpl` 渲染、`mmsg` 打包、Messenger 和
OneBot Adapter 投递合成图片，而不是直接绕过项目调用发送接口：

- 九张图片生成 1440×1440 九宫格，47,406 字节，成功投递。
- 四张 1440×8000 图片按顺序生成两张 1440×16000 长图，分别为
  20,349,071 和 20,145,757 字节，均成功投递。
- 两张长图合计 Base64 数据超过 50MiB，Messenger 按 JSON 字节预算拆成两次请求；
  请求参数分别为 27,132,385 和 26,861,128 字节。
- 三张输出从 QQ CDN 下载后，字节数及 SHA-256 均与本地产物完全一致。

Satori Adapter 也成功投递了同一张 1440×16000、20,349,071 字节的长图。
回读时发现 Satori 图片标签内的 CDN URL 使用 `&amp;` 编码查询参数，项目原属性解析
没有还原 HTML 实体，导致下载请求返回 400。已统一还原标签属性中的实体并补充回归测试；
还原地址后只读下载验证 SHA-256 与本地产物一致，未重复发送已成功投递的图片。

本机发送账号的 QQ 图片查看器已成功打开 Satori 投递的该张长图。
1440×16000 是已验证可上传、原样下载及本机打开的尺寸，不代表 QQ 分辨率上限或独立接收端显示结论。
项目采用它作为保守的分页高度，且另设每页像素和源图解码预算，防止拼接时分配巨型画布。
自动化测试另外使用更小的编码预算验证长图按实际字节继续拆分，并验证总高度与内容顺序。
复现程序、样本与验证清单位于被 Git 忽略的 `debug/image-merge/`。
