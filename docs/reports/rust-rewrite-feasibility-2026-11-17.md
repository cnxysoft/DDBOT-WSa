# DDBOT-WSa 使用 Rust 优化与重写的可行性报告

调研日期：2026-11-17。分支：`next-dev`。基准提交：`f06149323ce2462f10eb424ed3780114b8360462`。

范围：当前 DDBOT-WSa 仓库，包括订阅源、命令与权限、模板、数据库、OneBot / Satori / QQ 官方适配器、Telegram、管理面板、图片与 FFmpeg。本文评估迁移，不实施重写，不修改运行数据。

## 1. 结论与建议

**技术上可以用 Rust 重写；以“优化性能”为主要目标，目前没有足够证据支持立即全量重写。推荐先测量、再迁移高收益模块，同时保留演进为 Rust 主程序的路径。**

项目已经使用 Go 的并发运行时和原生 FFmpeg。网络轮询、平台限流、媒体下载与上传是否占主要耗时尚未测量；换语言无法直接缩短这些外部等待。Rust 的主要潜在价值是更明确的资源与任务生命周期、减少部分堆分配，以及在图片处理等计算路径中尝试更高效的实现。

当前迁移成本最大的部分是行为兼容：定制的 Go 模板执行器、BuntDB 语义与历史数据、QQ 官方身份映射、平台 Cookie / 签名 / 会话状态，以及 9 个系统架构组合的媒体分发链。

建议按目的选择：

| 目的 | 推荐路线 | 判断 |
| --- | --- | --- |
| 降低现有部署 CPU / 内存，尽快交付 | Go 内优化 + 单个 Rust 热点验证 | 最符合当前证据，投入与回退成本较低 |
| 长期建立更清晰的模块生命周期和配置体系 | 渐进迁移，先定义协议与状态边界 | 可行；收益主要来自架构改造，Go 中也能实现相当一部分 |
| 建立以 Rust 为主的新一代产品 | 独立 Rust 核心，按平台和功能迁移 | 可行，需要明确兼容等级和长期维护预算 |
| 保持当前全部行为、旧模板和部署目标，直接一次性替换 | 全量等价重写 | 风险高，不建议作为首次交付方式 |

投入级别的初步判断：

- 性能基线 + 一个 Rust 候选模块的验证：约 **2–4 周**，1–2 名熟悉相应模块的工程师。
- 明确收窄功能的 Rust 核心 MVP：约 **8–12 周**，2 名熟悉 Go / Rust 的工程师；不能宣称已经替代现有完整版。
- 当前功能大体对齐、旧数据和模板有兼容方案的生产替代版：初估 **17–32 人月**；3 名熟练工程师约 **7–12 个月**，2 名约 **10–18 个月**。这是范围估算，不是已完成原型后的交付承诺，详见第 9 节。

## 2. 现有工程规模与结构

### 2.1 代码规模

统计口径：仓库中的 Go 文件，排除 `.git`、`node_modules`、`testdata`；按物理行统计，包含注释和空行。实现行排除 `*_test.go` 和 `*.pb.go`，但包含定制 / 派生代码，不能直接换算为重写工时。

| 范围 | 非测试、非生成实现行 | 说明 |
| --- | ---: | --- |
| `lsp/` | 51,567 | 核心、12 个订阅平台、模板、权限、持久化等 |
| `adapter/` | 16,851 | 消息抽象、WebSocket、OneBot、Satori、QQ 官方 |
| `admin/` | 3,444 | Go 后端；不包含网页 JS / HTML / CSS 的行数 |
| `utils/` | 2,298 | 含图片处理及系统辅助逻辑 |
| 其余 Go 实现 | 4,403 | bot、FFmpeg、请求层、图池、代理等 |
| **Go 实现合计** | **78,563** | 约 7.9 万行 |

另有 214 个测试文件、37,620 行测试，以及 21,081 行生成代码；合计 534 个 Go 文件。仓库有 6 份 `.proto` 和 30 份内嵌默认模板。

`lsp/template` 约 6,617 行、`lsp/twitter` 约 6,469 行、`lsp/bilibili` 约 6,167 行，均为上述非测试、非生成物理行。单个平台不是简单的 HTTP 请求封装。

仓库实际有 5 个 `go.mod`：根模块、`bot`、`adapter`、`lsp/eventbus`、`utils/qqlog`。模块间存在本地 replace 和业务依赖；Go package 的边界不等于可直接移出的独立服务边界。

### 2.2 主处理链路

```text
application 配置 / 管理面板
        ↓
平台轮询、Cookie / 签名 / 客户端会话
        ↓
Event → 订阅匹配、权限、过滤、去重、通知策略
        ↓
Notify → 模板与富消息 → 图片合并 / 媒体处理
        ↓
发送限流与离线队列 → OneBot / Satori / QQ 官方 / Telegram
        ↕
订阅、权限、去重、计数、身份映射及历史数据
```

依据包括 `lsp/concern/concern.go` 的 Event / Notify / Concern 接口、`lsp/concern/stateManager.go`、`lsp/notify.go`、`lsp/mmsg` 与 `adapter/interface.go`。

这里适合保留“平台采集 → 领域事件 → 消息计划 → 适配器发送”的结构，但不宜逐行把 goroutine、全局变量和动态类型翻译成 Rust。

## 3. 性能收益：哪些值得验证，哪些不能承诺

### 3.1 目前证据不足以认定 Go 是主要瓶颈

项目在 `cmd/main.go:25` 引入 pprof，`--debug` 时在 `localhost:6060` 提供调试接口；Makefile 和 CI 使用 `-pgo=auto`，但本次没有发现提交的 `.pgo` / CPU / heap 性能样本。

仓库目前能检索到的 Go `Benchmark*` 只有 `adapter/wsclient_test.go` 中两个。未发现覆盖平台轮询、模板、图片合并和持久化的完整基准套件。本次没有连接线上实例，因此没有 RSS、GC、CPU 占比、尾延迟或业务吞吐的生产基线。

本次执行现有微基准，环境为 Windows amd64、Go 1.26.2、Intel i7-1195G7，`CGO_ENABLED=0`，每项 300ms、重复 3 次：

| 基准 | 实测范围 | 分配 |
| --- | --- | --- |
| `WSClient_HandleMessage` | 1,209–1,364 ns/op | 448 B/op、7 allocs/op |
| `WSClient_ResponseChOps` | 126.1–133.7 ns/op | 120 B/op、2 allocs/op |

前者对固定的小 JSON 消息执行同步处理，handler 为空；后者只测响应 channel 的创建、登记和删除。两者均不含真实 WebSocket 传输、完整事件解析、模板、API 请求和消息上传，也没有测并行压力。

**这些结果只能作为局部基线，不构成 Rust 更快或现有 Go 整体足够快的证明。**

### 3.2 候选优化位置

| 路径 | Rust 潜在价值 | 限制与优先级 |
| --- | --- | --- |
| 图片解码、缩放、排版、JPEG 编码 | SIMD 库、缓冲复用、像素生命周期管理 | 值得首先验证；须和 Go 中换库 / 限并发 / 减少复制同时比较 |
| Anubis SHA / HashX 计算与 WASM 执行 | 本地哈希实现和运行时选型可能改善 CPU | 只有实际占比较高时值得迁移；不能靠增加请求频率获得收益 |
| JSON / HTML 解析与消息转换 | 强类型模型和更少临时分配 | serde / 解析器仍有分配，不能假定低复制一定成立；平台兼容测试优先 |
| 调度、队列、去重和限流 | 显式所有权、背压、任务取消 | 主要是架构质量收益，Go 也能实现；Rust 不会自动消除逻辑竞态 |
| 数据库访问 | 新索引或减少扫描可能改善吞吐和内存 | 换存储会改变延迟、持久化和事务语义，不是语言层面的免费收益 |
| 视频 / GIF 转换 | 更清晰的任务隔离、超时和资源管理 | 当前已调用原生 FFmpeg；换成 Rust 包装不会让相同编码器自动提速 |
| 平台 HTTP、代理、下载上传 | 连接池、合并请求、缓存能改善部分开销 | 平台响应、轮询周期和速率限制仍存在；Rust async 与 Go 都适合 I/O |
| 模板执行 | 可设计更受控的 IR 和执行器 | 兼容成本高，不适合第一个“提速”模块 |

图片处理当前已有像素预算、分页、解码复用、LRU 与 singleflight：见 `utils/image_merge.go`、`lsp/mmsg/image_merge_cache.go`。不能把已存在的优化当成 Rust 迁移后的新增收益。

以内存为例：默认上限 24,000,000 像素，单个 RGBA 画布约 96MB；48,000,000 像素约 192MB，尚不含源图片、编码缓冲和并发任务。这类容量需求不会因 Rust 没有 GC 而消失。控制同时运行的媒体任务和总像素预算，可能比换语言更直接。

若某可优化部分占总 CPU 时间的 20%，即使该部分变为 3 倍快，Amdahl 定律给出的整体 CPU 工作吞吐增益也只有约 1.15 倍；这还是假设没有额外集成开销的理论值，不能等同于推送延迟改善。

### 3.3 先建立公平的评估方法

至少分开测量：轮询计划到开始、请求耗时、解析、状态判定、模板、媒体处理、发送排队、IM 上传。按 100 / 1,000 / 10,000 个模拟订阅、不同群扇出、文本与图片场景做离线回放；这些是测试负载档位，不表示当前或未来产品容量。

Go / Rust 使用相同硬件、输入、并发、缓存冷热状态、压缩质量和限流；使用优化构建，分别测纯计算与完整 IPC / FFI 调用成本。指标包括 p50/p95/p99、CPU 时间、峰值和稳态 RSS、分配、队列深度、错误率及输出质量。混合方案要统计 Go 和 Rust 两个进程的总资源。

Go 侧应先验证连接复用、缓存命中、渲染扇出、背压与媒体并发的改善空间，再比较语言实现；不能把修复低效算法后的收益全部归因于 Rust。

建议 PoC 的继续门槛：目标模块在真实负载中的资源占比足够高，并且计入边界开销后，相关 CPU 或峰值内存有至少约 20% 的改善，或显著解决既定容量问题；完整业务链路没有明显退化。该数值是建议的立项门槛，不是性能预测。

## 4. 主要兼容性障碍

### 4.1 定制 Go 模板是首要障碍

`lsp/template/README.md` 明确说明它是 `text/template` 的 fork。`template.go`、`exec.go` 使用 Go parser、反射、方法调用和 Go 值的真值 / 空值 / 数字语义。

它还不是纯文本渲染：

- `exec.go:35` 的输出是 `*mmsg.MSG`；`printValue()` 在 `exec.go:971` 识别 `adapter.IMessageElement` 并追加富消息。
- `pic`、`at`、`video`、`forward` 等函数生成消息元素。
- 成员查询、网络请求、文件读写、积分和数据库函数具有外部副作用。
- 默认模板和旧用户模板可能依赖 Go 对象字段、导出方法、管道、变量、`range`、`with`、错误传播及缺失值行为。

因此 Tera、MiniJinja 或任何声称类似 Go 模板语法的 crate，都不能直接替换当前执行器并保证兼容。

可选方案：

| 模板路线 | 优点 | 代价 |
| --- | --- | --- |
| 暂时保留 Go 模板 / 相关平台管线作为受控 worker | 可最大限度保留旧行为 | 仍需分发 Go，IPC 和对象重建有成本；副作用和数据库要有唯一归属 |
| Rust 实现有范围的 Go 模板兼容层 | 最终可形成 Rust 主程序 | 高成本，需要逐项语义和富消息验证；不能把“能解析模板”当成“兼容” |
| 引入新版模板语言并提供迁移器 | 新架构清晰 | 属于产品兼容性变更；迁移器不能保证自动转换全部自定义函数和对象方法 |

短期建议保留旧模板路径；若目标最终要求完全移除 Go，必须为兼容解释器或新版模板迁移单独立项。

把模板输入序列化成 JSON 并不能保留 Go 方法和反射能力。保留 Go worker 时，要么连同依赖这些对象的平台 / 渲染段一起保留，要么设计明确的字段、方法能力和副作用 RPC 协议，不能假定只传一份 map 就能工作。

### 4.2 BuntDB 需要语义迁移，不能直接改用 SQLite 打开旧文件

当前 `.lsp.db` 和可选扩展库由 BuntDB 管理，包含键值、JSON、过期时间、条件写、原子计数、索引和排序集合等。`lsp/buntdb/shortcut.go:69` 起还通过 goroutine local storage 传递事务上下文。

Rust 侧可考虑 SQLite，也可评估纯 Rust 嵌入式 KV，但没有必要先承诺完全兼容 BuntDB 的文件、TTL、排序和事务 API。简单 KV 替换也无法自动保持这些语义。

建议迁移路径：

1. 初期保留单一存储所有者；Go 和 Rust 不同时直接写同一数据库文件。
2. 用 Go BuntDB 读取器导出版本化数据，保存原始 key/value 字节、绝对过期时间、领域 schema 和校验信息。可用 base64 字段避免字符串编码导致字节损失。
3. 停止写入并做一致性快照，导入新库后重建索引；TTL 按绝对时刻恢复，已过期条目不复活。
4. 分领域检查订阅、权限、过滤规则、去重、积分、计数器、告警和自定义扩展数据。
5. 原文件只读保留。切换后若新库已经写入，回滚必须反向导出增量或恢复到切换快照并明确数据损失窗口；不能只换回旧二进制就称为无损回滚。

异步 Rust 中应显式传递 transaction / repository，而非模仿 goroutine-local 全局事务；task 可能跨线程调度，锁或事务也不应跨无界网络等待。

### 4.3 QQ 官方身份映射必须稳定继承

`adapter/qqofficial/idmap.go` 将 `(appID, openid)` 映射为单调递增的内部 int64；序列化键使用 `\x1f` 分隔符。状态保存在 `.qqofficial-state-<app-id>.json`，含群清单和备份恢复策略。

旧订阅与权限依赖这些内部数字。新程序不能重新分配、哈希替代或仅迁移 `.lsp.db` 而遗漏这份映射。还需保留机器人身份指纹、防止不同机器人复用同一工作目录的现有约束。

QQ 官方发送还涉及原始字符串消息 ID、被动回复锚点、回复额度和窗口、事件 ID、序号、媒体上传、心跳与 Resume。见 `adapter/qqofficial/adapter.go`、`message.go`、`ws.go`。普通 WebSocket 客户端库只能提供传输，不能代替这些业务协议。

### 4.4 平台模块的复杂度主要来自状态与协议细节

12 个订阅平台包括 Bilibili、ACFun、斗鱼、虎牙、YouTube、微博、Twitter、抖音、小红书、Twitch、TwitCasting、小黑盒。Rust 生态中有 HTTP / HTML / OAuth 等基础库，但不能假定有与本项目逐项等价的平台 SDK。

重点风险：

- 扫码与 Cookie 更新、账号有效性恢复、自动刷新后台任务。
- Twitter 镜像选择、冷却、翻页、API 模式、翻译、验证码工作量计算与媒体管线。
- 小红书签名的字段顺序、URI 编码、整数位宽、溢出、随机状态和时间戳。
- B 站动态类型、关注同步、WBI 等签名和启动去重策略。
- 各站点对“开播 / 下播 / 标题变更 / 历史动态”的判定与抑制逻辑。

`lsp/xhs/crypto/signature_regression_test.go:9`、`:36` 已有 URI 和 JSON 顺序的固定期望。Rust 需要字节级兼容向量，不能只比较 JSON 解析后的等价对象；Go 的整数 / 序列化语义与 Rust 默认实现未必一致。

6 份 `.proto` 可保留为模型资产，但不能等同于直接替换序列化库：项目部分接口用 Go `protojson` 解析平台 JSON，Rust `prost` 本身不提供完全相同的 JSON 映射。int64、未知字段、枚举、默认值和缺失字段需额外兼容测试。

### 4.5 FFmpeg 和 WASM 会影响部署与内存模型

当前有 CLI 与 cgo 两条媒体路径：CLI 调用系统 FFmpeg；cgo 链接仓库约定的 FFmpeg / OpenSSL 静态库。MP4 主要复制压缩流，GIF 使用原生解码 / 编码。见 `ffmpeg/ffmpeg_cli.go`、`ffmpeg/ffmpeg_cgo.go` 和 `ffmpeg/README.md`。

Rust 可继续调用 FFmpeg CLI，或封装 C ABI。若选择 bindings，需要检查 FFmpeg 7.1.5 的 ABI、头文件、库构建选项、回调、取消和错误资源释放。FFI 不会因宿主语言改为 Rust 就变成 safe Rust；C 库越界、崩溃和缓冲峰值仍可能存在。

Anubis HashX 当前用 wazero，限制模块大小、执行超时、内存 32MiB，并只导入指定 host function，不开放 WASI 文件 / 网络能力，见 `lsp/twitter/anubis.go:198`。Rust 可评估 `wasmi` 或 `wasmtime`，但应分别验证目标平台、指令集、编译 / 实例化开销、执行中断、host ABI 和相同的内存限制；不能只替换调用名称。

### 4.6 配置与任务管理需要重新设计

上一份[热重载报告](global-config-hot-reload-2026-11-17.md)已经确认：共享 Viper、初始化缓存、写入忽略窗口及 Windows 文件替换事件存在问题。Rust 中采用 `Arc<ConfigSnapshot>`、变更通知和模块 supervisor 有助于形成清晰边界，但这些是需要显式实现的设计。

Rust 类型系统可以减少 safe Rust 中的非同步共享读写，不能自动保证版本一致、无死锁、不重复通知、资源准备失败回退或外部服务幂等。

配置兼容还包括大小写归一化、缺省值、Go duration、空字符串 / null、站点别名、未知字段和实际加载路径。用户旧 YAML 不能直接按 Rust 字段名严格反序列化后就宣称兼容。

### 4.7 管理面板可复用，但后端接口要保持契约

`admin/web` 是可复用的静态资产，现有 Go 后端内嵌分发，见 `admin/static.go`。Rust 可以继续内嵌这些文件。

需要迁移的是 API 路径、字段、数值精度、错误状态、鉴权、首次初始化条件、配置脱敏 / 写入规则、SSE 日志与推送记录、模板编辑和预览。Rust 可以内部用 i64，但对网页返回 int64 时要保持既有可用性，并为超出 JavaScript 精确整数范围的值制定字符串协议；不能只换数据库类型。

接口兼容测试通过前，不能把“页面能打开”视为管理功能已迁移。

## 5. Rust 技术选型候选

以下是方案候选，不是已完成编译和所有目标平台验证的依赖清单。不固定未经核验的“最新版本”。

| 能力 | 候选 | 项目需要补齐的部分 |
| --- | --- | --- |
| 异步运行时、连接与任务 | Tokio、tokio-util | 明确 supervisor、取消、背压、任务退出与重试策略 |
| HTTP 管理端 / SSE | Axum、Tower | 保持现有 API 与鉴权、状态码、SSE 和嵌入资源行为 |
| HTTP 客户端 | reqwest + rustls / native TLS | 验证连接池、CookieJar、代理、HTTP2、系统证书和平台兼容；rustls 不保证更少依赖或所有目标免工具链配置 |
| WebSocket | tokio-tungstenite 或框架 WS | Echo 请求关联、超时、断线恢复、认证、队列及协议状态自行实现 |
| JSON / 数据模型 | serde、serde_json | 保持 int64、字段缺失 / null、顺序敏感签名与领域类型 |
| protobuf | prost，按需补 JSON 映射层 | 验证 Go protojson 行为；禁止未经比较的默认自动派生替换 |
| 文件监听与配置快照 | notify、ArcSwap / watch | 目录监听、替换 / 删除 / 重建、防抖、完整校验和旧版本保留；YAML parser 的维护状态和 serde 集成需 PoC 核验 |
| 持久化 | SQLite + rusqlite / sqlx，或另评估嵌入式 KV | TTL、事务、索引、序列和旧数据导入。同步数据库调用放专用线程；异步接口也需控制连接与事务占用 |
| 图片 | image、fast_image_resize，按需要评估编码器 | 质量、裁剪、透明背景、色彩、像素和输出字节预算均需对比 |
| HTML / URL / 签名 | scraper、url、经验证的加密基础库 | 平台抓取规则、编码和签名不是基础库自动提供 |
| 日志与追踪 | tracing、tracing-subscriber | 文件轮转、字段、脱敏、管理面板日志桥及 FFmpeg 原生日志 |
| Telegram / OAuth / cron | 可选 SDK 或直接协议实现 | SDK 可覆盖基础通信，但命令路由、状态、时区、cron 语义仍需验证 |
| WASM | wasmi / wasmtime | 执行预算、资源隔离和目标平台可用性 |
| 旧模板 | Go 兼容 worker / 独立兼容解释器 | Tera / MiniJinja 只适合明确的新模板方案 |

建议领域数据使用显式枚举与结构：平台用户 ID、QQ 内部 ID、原始 openid、Telegram chat ID、消息 ID 分别建模。迁移兼容层保留旧 int64 键关系，不能在领域重构时顺便重新编号。

## 6. 迁移方式比较

| 路线 | 优点 | 代价 / 限制 | 适用判断 |
| --- | --- | --- | --- |
| 保持 Go，优化架构与热点 | 兼容风险和交付成本最低 | 无 Rust 主程序，仍有 Go GC | 应作为性能比较的控制组 |
| Rust 独立 worker，Go 调用 | 边界清晰、崩溃隔离、按模块切换 | 双进程分发、IPC、总 RSS 可能增加；大图传输和重复缓存需控制 | 推荐首次验证图片等独立计算模块 |
| Go → Rust C ABI | 可减少进程通信，保留主程序 | cgo、内存所有权、panic 边界、跨平台静态库更复杂；失去该混合构建的纯 Go 无 cgo 路径 | 仅在 worker 边界开销有证据成为瓶颈时考虑 |
| Rust → Go 兼容服务 | Rust 逐步成为主程序，可保留旧模板和采集段 | Go 仍需维护；状态和副作用 RPC 设计复杂 | 适合长期渐进路线 |
| 一次性 Rust 全量重写 | 最终可形成统一运行时 | 回归面最大、长期双线维护，切换前很难证明全部等价 | 不推荐起步 |

Rust worker 建议先使用本机受控 IPC 或带长度和版本的 stdin/stdout 协议，调用要有 request ID、超时、取消、最大消息尺寸和错误映射。大图优先传压缩字节或有生命周期的临时文件句柄 / 路径，避免把百 MB 像素缓冲转成 JSON base64；只有实际需要时再引入共享内存。

C ABI 方案应让每个缓冲明确由哪一端分配和释放，不跨边界传 Rust trait、Go interface、slice 内部布局或异步任务引用。Rust panic 不能越过 C 边界，`catch_unwind` 也不能恢复 abort 或底层 C 崩溃。原有 `CGO_ENABLED=0` 发布形态需要继续提供纯 Go 回退或独立 worker 版本。

保留 Go worker 的混合方案，应明确命名为“渐进迁移版”；只有消除运行时 Go 依赖后，才可称为完整 Rust 实现。

## 7. 推荐目标架构

```text
Rust 应用装配与进程生命周期
  ├─ ConfigManager：候选配置、校验、差异、生效快照
  ├─ PlatformSupervisor：每站点任务、凭据、取消和重试
  ├─ SubscriptionRepository / PermissionRepository / DedupStore
  ├─ EventPipeline：订阅匹配、过滤、通知状态
  ├─ Renderer：旧 Go 兼容路径 / 新模板 → MessagePlan
  ├─ MediaService：受资源预算限制的 CPU / FFmpeg 任务
  ├─ Dispatcher：按目标顺序、全局和平台限速、发送状态
  ├─ Adapters：OneBot、Satori、QQ 官方、Telegram
  └─ AdminAPI：现有前端、配置状态、SSE、推送历史
```

MessagePlan 应是版本化的富消息结构，例如 Text、Image、At、Reply、Forward、Video，而非把所有平台都压成一段字符串。图片与媒体用受管理的资源引用；明确站点、身份和输出字节限制。

网络 I/O 使用异步任务；图片计算使用受限 CPU worker；FFmpeg 子进程 / 原生调用与 WASM 执行有单独预算。不能把所有 CPU 密集任务无限制 `spawn_blocking` 后就认为已有背压。

发送器必须区分平台配额、目标消息顺序、重试、离线缓存过期和未知发送结果。数据库事务与外部 IM 发送之间没有天然分布式事务，不能无条件保证 exactly-once；应明确定义去重键、重试上限和可接受的重复 / 遗漏处理策略。

## 8. 分阶段落地

### 阶段 A：基线与兼容资产

建议用 1–2 周完成：代表性 CPU / heap profile、网络与队列分段指标、图片和模板回放样本、配置字段清单、领域状态 schema、API 契约与最重要的历史回归向量。

优先复用现有图片布局 / 字节预算、小红书签名、QQ 官方状态恢复、Twitter 媒体管线等测试资产。Go 测试需要转换为跨语言数据向量或协议测试，不能原样交给 Cargo 运行。

### 阶段 B：一个独立 Rust 模块的 PoC

首选图片合并 / 缩放 / 编码，包含长图和网格、透明源图、压缩质量、像素 / 字节预算和并发相同图集。可将签名或哈希作为更小的语义验证样本，但没有性能占比证据时不优先产品化。

PoC 与 Go 优化版本比较纯算法和完整调用两层成本。保持 Go 回退；收益达不到门槛时，可以停止 Rust 迁移并保留收集到的基线和 Go 优化。

阶段 A + B 目标窗口为 2–4 周；若先补测试样本或依赖工具链超出预期，需要重估，不能以未完成的对比支持全量重写。

### 阶段 C：Rust 核心 MVP

如果长期目标明确为 Rust 主程序，先实现 OneBot v11、基础订阅与权限、配置生命周期、存储抽象、日志 / 指标，接入斗鱼和 B 站基础直播场景，再逐步扩展。

建议 MVP 明确不包含：全部平台、全部 B 站动态、旧自定义模板完全兼容、Satori / QQ 官方完整适配、Telegram 全部行为、内置 FFmpeg 全架构等。这些不是删除需求，而是作为后续里程碑逐一交付。MVP 必须给出功能清单，不能仅凭“能发推送”替代旧产品。

### 阶段 D：影子回放与分批切换

先重放已经捕获并脱敏的输入，让 Go / Rust 输出规范化事件和消息计划进行比较。避免两套程序独立登录、关注账号、重复轮询或同时对外发送。

模板有文件、网络、积分和 DB 副作用；影子执行要模拟 / 记录这些操作，不能直接把同一生产模板运行两遍。

按站点和适配器切换时，对每个发送目标只保留一个有发送权的实例，冻结并迁移状态，排空或明确处置旧队列。只迁移持久化状态并不能继承内存中的离线消息、被动回复额度或进行中的发送结果。

切换后至少观察 2–4 周，覆盖重连、Cookie 过期、配置变更和重启恢复；长期 token 刷新与罕见恢复路径用可控时间和故障注入补齐，不能靠短期在线稳定推断全部路径正确。

### 阶段 E：生产替代与清理

全部声明支持的功能通过验收、数据迁移与回滚演练后，再按实际使用情况停止旧模块维护。模板和状态兼容没有完成前，保留相应 Go 服务并持续版本化接口。

## 9. 工作量与经济可行性

假设：熟悉现有业务和 Rust 的工程师；复用现有网页与测试资产；完整目标涵盖当前平台、适配器、旧数据以及有明确边界的模板兼容方案；不从头开发视频编解码器。

| 工作包 | 初步工程日 |
| --- | ---: |
| 性能基线、样本、协议与兼容范围 | 10–20 |
| Rust 工程、配置、生命周期与可观测性 | 15–25 |
| 订阅、过滤、权限、去重与调度核心 | 20–40 |
| OneBot 与统一富消息模型 | 15–25 |
| Satori、QQ 官方、Telegram | 30–50 |
| 12 个平台的采集、会话和恢复行为 | 60–100 |
| 模板兼容 / 迁移工具与副作用边界 | 40–80 |
| 数据库语义、历史数据与回滚迁移 | 20–35 |
| 管理 API、SSE 与前端对接 | 10–20 |
| 媒体、WASM 与跨平台依赖接入 | 20–35 |
| CI、故障回归、灰度和迁移验收 | 25–45 |
| **合计，不含预备量** | **265–475 工程日** |

按每人月 20 工程日，并加约 25%–35% 的协议变更、兼容和返工预备量，得到约 **17–32 人月**。如果要求对任意第三方 Go 模板及其对象方法做到严格等价，或增加完整双向数据库兼容，上限仍可能继续上升。

2–3 人不是线性加速：架构、状态模型、模板和迁移存在前后依赖，还要维护现有 Go 版本以跟进平台接口变化。上述 MVP 的 8–12 周与完整版工作包存在重叠，不应简单相加。

预算可按“17–32 × 团队每人月综合成本”估算开发部分，再纳入发布设备 / 测试资源和持续维护。不要只按部署机器每月节省的内存计算回报；若项目部署量不大，单靠资源费用通常很难证明这么大的重写投入划算。

若团队没有熟练 Rust 工程师，应先通过 PoC 观察学习、调试和发布成本，再给正式排期。Rust 缺少业务经验或 Go 缺少性能分析经验，都不能用语言本身补齐。

## 10. 生产验收与退出条件

| 维度 | 验收重点 |
| --- | --- |
| 功能 | 明确平台 × 事件类型 × 命令 × 适配器支持矩阵；核心流程对比旧行为 |
| 模板 | 默认模板、典型用户模板、富消息元素、副作用、缺失值和错误路径；声明不兼容项有迁移办法 |
| 数据 | 订阅、权限、去重、TTL、计数、积分、身份映射及扩展库的导入数量与内容核对 |
| 恢复 | 重连、超时、未知发送结果、断电、损坏状态文件、Cookie 失效、模板错误与数据库异常 |
| 性能 | 固定负载下比较 p95/p99、总 CPU、总 RSS 和错误率；把 IPC、双运行时和媒体资源算入 |
| 长期运行 | 无持续 RSS 上升、任务泄漏或队列无界增长；配额和重试按设计收敛 |
| 发布 | 首期 Windows amd64 / Linux amd64，后续覆盖全部已承诺目标；检查原生库 ABI 和动态依赖 |
| 回滚 | 实际执行切换 / 回退，说明回退后状态是否完整、需要重放什么、何时禁止直接回退 |

出现以下情况应缩小或停止全量迁移：热点不明显或 Go 优化已满足目标；Rust 在计入调用边界后没有足够收益；旧模板兼容投入超预算；迁移不能保证身份 / 权限正确；依赖无法覆盖必须支持的目标架构。

现有发布目标是 Linux amd64 / 386 / ARMv7 hard-float / ARM64、macOS amd64 / ARM64、Windows amd64 / 386 / ARM64。Rust 编译器存在对应或相近 target，不代表所选数据库、TLS、FFmpeg 和 WASM runtime 都能直接构建。尤其不能将现有 MinGW 静态库默认视为可直接链接到 MSVC 目标；应统一 ABI / CRT 或重新构建匹配库。相关 CI 必须逐目标验证。

沿用现有代码、模板和素材时需保留相应许可证与来源；Rust 改写不会自动改变现有项目的 AGPL-3.0 及所复用组件的许可证要求。原生媒体依赖的构建选项和许可证记录也应纳入现有发布维护流程。
